# 用户语需求文档

交付给产品读者看的**需求文档**，按需配套给开发者或 AI 落地的**技术文档**。二者都是导出物，不进入项目记忆、不建索引；技术文档单向关联需求文档，需求正文独立可读。本技能写文档，不实施需求。

## 定界

一次运行只处理一个主题，选一种入口：

- **规划**：需求还没做。核实现有能力后澄清目标行为；意图本身还模糊时先走 `/cs-goal`。
- **整理**：需求已做完或进行中。先核实真实实现，再写完整草稿，未决点随稿提出；没有用户可感知变化时如实说明，技术细节留给可选伴生文档。

需求文档由用户指定落点，否则 `<仓库根>/docs/需求/<用户叫它的名字>.md`；技术文档默认在需求文档同目录，名为 `<需求文件主名>.技术.md`。已有目标先读，只更新同主题内容。用户只要求给已有需求补技术文档时，以该需求为基线，不重写需求正文；只有技术主题而没有对应需求时，先确定需求范围与基线。

**完成条件：入口、主题、需求读者与基线明确，本轮输出文件已按下面的技术分支确定。**

## 技术分支

用户明确意愿优先于材料是否齐全：

| 输入 | 本轮产出 |
| --- | --- |
| 明确需要技术文档 | 必须配套或补写；信息不足先查证，再访谈补齐 |
| 明确不需要技术文档 | 仅需求文档，即使提供了技术信息 |
| 未表态，但主动提供了接口、字段、桥接或实现方案等相关材料 | 可以配套生成，并说明本轮选择；若需扩大技术访谈，先确认是否需要 |
| 未表态，也没有提供技术材料 | 默认仅需求文档；自行从代码查到技术事实不触发生成 |

已有伴生文档不等于本轮授权更新。无论是否生成技术文档，都要完成下述事实探索；选择生成时，读取并遵循[技术文档](references/technical-doc.md)。

**完成条件：生成或不生成有明确依据；需要补齐材料时，没有把“缺信息”当作取消用户所需技术文档的理由。**

## 取材

用户原话决定目标与词源，当前实现用于核实现状；在工作上下文区分**已有事实、已确认目标或方案、推测、未知**，不能把现状自动当成目标，也不能把期望写成已实现。

围绕每条需求行为查证，而不是只读变更摘要或命中的文件名：

- 从入口沿相关调用链追到关键处理与结果，核对能力的提供方和消费方、接口与类型、字段映射、配置约束，以及相关成功、失败和空状态。涉及桥接、存储或外部服务时，追到对应边界。
- 用实际处理代码核实声明，再以测试、配置、界面文案和现有文档交叉检查；材料冲突时查清实际路径，保留仍需决定的差异。整理已完成需求也执行同样的探索。
- 每个拟提问题先检查能否从上述证据解答。能查到的自己查；查不到时记录已查范围和缺少的来源，不能把未搜索当成未知。
- 查到足以确定本主题的行为、关键约束和分支即停止；不扩张为全库扫描。没有仓库、权限或外部资料时，如实说明边界，只索取具体缺失材料。

**完成条件：每条拟写行为都有用户明确决定或可核实证据，相关关键实现链路已查明或缺口有明确原因；可自行查证的问题已消除。**

## 澄清

需要产品决定，或已选择技术分支且存在落地决定时，按 [grilling](../grilling/SKILL.md) 的设计树与轮次推进；技术文档涉及的实现契约和关键分支同样进入设计树。仅写需求文档时，技术探索用于核实产品行为，不额外发起无关的实现方案访谈。

只问证据与既有约束无法确定、且会改变产品行为或实现契约的决定，以及确实不可取得的外部信息。问题补充**已查事实、剩余缺口及其影响**，按 grilling 格式给推荐，避免泛问“接口怎么设计”“还有什么要补充”。已有明确答案不重复确认；普通实现细节沿用已核实约定。

规划时先闭合决定再定稿；整理时保留可读草稿，未决点随稿询问。涉及目标与现状冲突时，问清写目标方案还是现状说明，不静默替用户选择。技术实现阻塞项未闭合时，技术文档只能标为草稿。

**完成条件：所有影响本轮需求验收或技术交接的决定已闭合并获确认；否则明确仍在澄清，不宣称文档已可交接实现。**

## 需求成文

只写产品读者能理解、能观察或验收的最终行为；技术契约写入伴生文档，而不是塞进需求正文。

- 一词一义；词源为本次用户原话 > 界面文案 > 已发布文档。必要的产品、行业术语可以保留，首次出现用读者能懂的话解释；只有会改变含义的歧义才请用户选择，并给 2～3 个候选。
- 每行行为说清“在哪、做什么、看到或得到什么”；数字、限制、权限与例外落到相应场景。内部变化需要交代时，用一句用户语说明效果。
- 不写源码路径、函数名、协议字段或实现机制；对比只在必要时出现。顺序或分支适合用 Mermaid 时，节点用用户语，图外有文字兜底。
- 保持紧凑，删复述而不删关键规则；不以“一两屏”为由省略验收分支。

标题为用户叫它的名字，正文按以下结构组织，不适用的小节省略：

1. **一句话**：给谁看的一份什么说明，附日期。
2. **这是做什么的**：为什么做、做完之后的样子，一两句话。
3. **做完之后，你会看到什么**：核心行为，同时就是验收；包含限制、例外与失败时的用户结果。
4. **走一遍典型场景**：顺序或分支需要时出现，可配 Mermaid。
5. **明确不做**：用户语的范围边界。
6. **还没定的事**：仅保留确需用户决定的非阻塞项；阻塞项在澄清阶段解决。
7. **名词约定**：有过歧义消解时，说明用哪个词指什么。

**完成条件：非技术读者无需翻译实现概念，也不必打开技术文档，就能理解完整需求与验收。**

## 自检与确认

- 逐条核对需求行为的来源、观察方式和分支；没有把推测当成已确认规则。
- 扫需求正文中的代码、路径和机制痕迹并改写；产品术语按读者含义检查，不机械删除。
- 选了技术分支时，完成参考文件的门禁，并核对两份文档的范围、名词、限制与验收一致。
- 新增或修改的需求文档请产品读者通读，问“有没有看不懂的词？有没有跟你说的不一样的地方？”；只补技术文档时沿用已确认的需求基线。技术文档另行确认尚需决策的技术内容，不要求非技术读者替 AI 核实代码事实。按回答原地修订。

**完成条件：需求表达已由用户确认或沿用已确认基线；本轮选定的文档全部通过各自门禁，未生成或未更新的技术文档已说明，不附加索引、计划或项目记忆产物。**
