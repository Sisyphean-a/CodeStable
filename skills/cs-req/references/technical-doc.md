# 伴生技术文档

仅在 `cs-req` 已选择生成或更新技术文档时读取。读者是接手实现的开发者或 AI；目标是结合对应需求文档即可推进实现，无需反复询问关键契约。它不是只有接口的清单，也不承担产品需求正文的职责。

## 建立基线

读取对应需求文档和已查明的项目证据，以需求小节或验收项关联技术内容；在技术文档开头用相对链接指向需求文档，写明本次覆盖范围、日期，以及哪些能力已实现、哪些是待实施方案。需求正文无需反向引用技术材料。

- 已有事实给关键代码、类型、配置或测试锚点；外部契约给权威来源。示例须与契约一致。
- 新方案说明依据、选择理由和确认状态；推测不能写成现行契约。现状与目标不同，分别说明已有能力、缺口和拟改动。
- 用户只补了部分技术材料时，先核实已有项目能否补足，再按主技能的澄清规则处理剩余决定。明确要求技术文档时，不能把已提供的局部信息当作全部范围。

**完成条件：每项技术内容能对应需求，事实与方案分开，读者知道实现基于什么、要改变什么。**

## 覆盖实现契约

按需求涉及的能力组织正文，以以下维度检查完整性。只展开适用项；不为填模板发明接口、桥接、迁移或其他系统能力。会影响接手判断的“不适用”可一句说明，其余省略。

| 维度 | 需要说清的契约 |
| --- | --- |
| 能力与实现边界 | 需求到模块、入口、提供方和消费方的对应关系；已有能力如何复用，新增、修改或替换在哪里发生，哪些部分不改 |
| 接口与调用 | 适用的 HTTP 路由与方法、函数签名、事件或 IPC 通道；调用方向、同步或异步语义、前置条件、认证授权、输入输出结构、错误码与错误结构、副作用；必要的有效调用示例 |
| 字段与传参 | 对象与嵌套字段的名称、类型、必填性、可空性、默认值、枚举、单位和约束；值的来源、校验、转换、传递位置与返回映射；省略、空值和非法值分别如何处理 |
| 桥接与集成 | 两端及各自职责、通道或协议、消息结构、序列化与字段映射、调用和回调顺序；适用的生命周期、超时、断连、异常传播及清理 |
| 数据与状态 | 数据来源、标识与关联、读写位置、状态及迁移条件；适用的持久化、事务、一致性、并发、幂等、顺序、分页或缓存语义 |
| 失败与边界 | 需求相关的失败、空状态和边界输入；错误如何传播并映射到用户结果，超时与重复调用如何处理；重试或回退仅写已有或已确认策略 |
| 权限与安全 | 身份与权限边界、数据可见性、信任边界及输入校验；敏感信息处理，不写真实密钥或凭据 |
| 实现方案与依赖 | 关键处理和数据流、必要的方案取舍、项目约定、依赖或外部契约、配置与环境前提；涉及兼容或存量数据时说明影响、迁移与恢复方式 |
| 验证与验收 | 每个需求验收项对应的技术验证方法、必要数据、预期结果和已有测试入口；覆盖成功、相关失败、空状态与关键边界，区分已验证和待验证 |

复杂顺序或跨边界数据流可用 Mermaid 或时序图；图中命名与接口、字段正文一致，图外仍保留关键契约。

**完成条件：每个需求行为都有可执行的实现路径，涉及的契约已细化到无需猜测关键参数、数据去向、失败语义和验收方式；不适用维度未扩大需求。**

## 闭合缺口

把覆盖检查暴露的未决依赖带回主技能的 grilling 设计树，先核实事实，再问真正需要决定的部分。新决定影响接口、字段、桥接、数据或验收时，检查并修订所有受影响章节，而不是只补一句回答。

影响实现的公开契约、权限、数据语义、兼容性或关键验收仍未定时，显式标记草稿与阻塞原因，继续澄清；不能用大量“待定”“按实际情况”代替完整技术文档，也不能擅自补成确定方案。非阻塞项注明不影响哪些实现范围。尚未实施或运行验证，本身不妨碍方案成文，但必须如实标注状态。

**完成条件：落地必需的契约和决定均已闭合；剩余项不阻塞实现，且依赖范围与确认状态明确。**

## 交接门禁

定稿前，站在未参与对话的接手者视角，沿典型成功路径和相关失败分支走查：

- 只靠两份文档与明确引用的项目或外部证据，就能确定改哪里、调用什么、字段如何流转、失败如何处理以及如何验证；不依赖聊天中的未落盘答案。
- 技术方案覆盖全部需求验收项，没有额外产品规则；两份文档的术语、范围、数值、权限与例外一致，技术字段与产品术语需要转换时有映射。
- 接口、字段、桥接和示例互相匹配；关键事实有可定位依据，规划能力未被写成已实现，未运行检查未被写成通过。
- 阻塞项已解决，必要方案已确认；不可取得的关键外部契约仍缺失时，如实交付草稿并说明阻塞，不声称已可直接实现。

**完成条件：全部通过，才可称为“可交接实现的技术文档”；否则继续探索或澄清。**
