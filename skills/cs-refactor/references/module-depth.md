# 模块深度

当改动会新增、移动或删除模块边界时，用本参考判断抽象是否真正承载复杂度。目标是让调用者通过较小且诚实的 interface 获得足够能力，并把规则、错误、状态和验证集中在最适合拥有它们的地方。

## 判断方法

1. **列出调用者知识。** 写下调用者为正确使用 module 必须知道的参数、顺序、不变量、错误、配置、性能与副作用。**完成条件：interface 的真实认知成本可见。**
2. **做删除测试。** 想象删除候选 module：复杂度若散回多个调用者，module 在提供 leverage；复杂度若随转发代码一起消失，优先折叠该层。**完成条件：抽象有具体复用或集中收益，而非只换名字。**
3. **检查 locality。** 让同一业务规则、状态转换、错误策略和验证证据由一个语义所有者掌握。**完成条件：修改一个概念无需同步编辑分散的调用者。**
4. **证明 seam 真实。** 只有策略、外部系统、生命周期、安全边界或运行环境会独立变化时，才建立可替换 seam。当前只有一个 adapter 不自动否定 seam，但必须有具体变化来源；仅为假想扩展或方便 mock 不成立。**完成条件：每个 seam 都对应可说明的独立变化。**
5. **收紧 interface。** 删除透传方法、重复参数和泄漏的内部顺序，把不可避免的复杂度吸收到 implementation。不同职责若有不同变化原因，保持分开，不为追求“更深”而合并。**完成条件：调用者知道得更少，module 承担得更多，职责仍内聚。**
6. **统一测试面。** 契约测试和调用者穿过同一个公开 interface；只有内部算法本身拥有独立契约时才直接测试内部。**完成条件：测试不依赖无契约的 implementation 细节。**

## 依赖与副作用

- 在组合根创建具体依赖，在业务 module 中接收依赖；对象创建必须有一个明确位置。
- 让业务判断返回结果或 effect description，再由明确边界执行外部副作用；数据库写入、发消息等真实业务行为仍保留，只集中其触发与失败策略。
- 外部系统、持久化、安全和不可逆操作即使只有一个 adapter，也可以形成 seam；依据是风险与独立变化，不是 adapter 数量。

## 输出检查

边界方案应能回答：

- 哪些调用者知识被移入 module？
- 删除 module 后，哪些复杂度会散回哪里？
- seam 后面具体有什么会独立变化？
- 哪些规则、错误和副作用因此获得 locality？
- 哪些测试通过公开 interface 证明契约？

这些问题没有具体答案时，沿用现有边界或选择更小的改动。
